## 1. 两套体系，禁止混用

项目工作编号分两条互不相混的线。先判断动作属于哪一类，再选编号，不得自创第三套临时号。

### A 线 · 开发交付树（GitHub Issue，Phase 2 起强制）

> ⚠️ **本节内容已失效/被取代（2026-11-21 标定 · 2026-11-28 补充修订）**：`2026-11-21` 曾标定 `v1` 期间 `GitHub Issues` 默认关闭；**`2026-11-28` 业主已明确作废该临时关闭限制**（见 [`AGENTS.md §Bug/缺陷/跨端交接 GitHub Issue 强制建档规则`](../AGENTS.md)）。现行分工：模块级任务/DAG 仍由 [`P8-PROJECT-TASKS_全量任务分解台账.md §2`](audit/P8-PROJECT-TASKS_全量任务分解台账.md#2-全量任务分解主表切片-14--全十模块) `S` 号承接，**所有 Bug 修复、运行故障与跨端待办缺陷强制使用 GitHub Issue 追踪**；原文按冻结规则保留，本标注为唯一合法编辑。

面向**要写/改生产代码**的交付，自上而下三层：

| 层 | 名称 | Issue 标题格式（全拼前缀，禁止孤立简称） |
| :-- | :-- | :-- |
| 1 | Phase X | 阶段（Phase 1 数据/模型地基、Phase 2 交易工程……） |
| 2 | Task YY | 阶段内任务，对应一个 Spec 主 Issue：`Spec: Phase X Task YY - <描述>` |
| 3 | Ticket ZZ | 可独立演示的垂直切片：`Phase X Task YY - Ticket ZZ: <type>(<scope>): <描述>`，带 `Blocked by` 依赖 |

- 权威出处：《AGENTS.md》「Task 与 Ticket 显式全拼命名原则」、`docs/spec-update-process.md` §3.2。
- Phase 1 历史的小数点编号 `Task 1.1 / 1.2` 为冻结历史，向前兼容，不回改。

### B 线 · 治理 / 审计线（不进交付树）

面向**只读复核、核验、裁决、封盘、文档对账**等不动生产代码的动作，用治理工单 + 核验单/裁决单编号：

| 类别 | 格式 | 示例 |
| :-- | :-- | :-- |
| 治理工单 / 议题 | `Pn-NAME`（n 为治理批次，NAME 大写下划线短码） | `P7-W1-POOLPHASE`、`P6-TMIN-CV-LOCK` |
| 核验单 | `<父工单>-CHK-ZZ` | `P4-BLIND-AUDIT-CHK-01` |
| 裁决单 / 决议 | `<父工单>-VERDICT-RZ` 或沿用既有裁决令格式 | `P7-W1-B-CLOSURE-VERDICT-R1` |
| 波次（时序，非层级） | `W1 / W2 / W3`，见 `docs/ROADMAP.md` | 不得当作编号层级嵌套 |

- **B 线文档主编号只用 `Pn-NAME-CHK-ZZ`；A 线 `Ticket ZZ` 仅可出现在描述后缀与正文锚点中，不得作为主编号段。** 复核 A 线交付物的 B 线单据，正文首页必须写明对应 A 线 Issue 号。
- **纯审计复核不新开开发 Ticket**，不套 Phase-Task-Ticket。
- 实验内部步骤（对照、诊断子项）可作子名保留，但**不得单独充当工单/文档主编号**。

## 2. 硬性禁止项

1. 禁止自创 `T3`、`P-1/P-2/P-3`、`E8-a/E8-b`、`D-1/D-2`、`L0/L1/L2` 这类脱离两套体系的临时号作为工单或文档主标题。
2. 禁止 B 线审计项塞进 A 树（不为纯复核开 `Phase X Task YY - Ticket ZZ`）。
3. 禁止 A 线 Task/Ticket 使用孤立简称（单独 `Ticket 01`、隐式缩写）。
4. 禁止同一文件/工单跨线混用两种编号体系。
5. 已封盘历史件不回改文件名与正文，只在本规范或台账加映射注。

   - **单向引用**：下层规格、执行与治理文档可引用 `ROADMAP.md` 阶段/波次定义；`ROADMAP.md` 不得反向承载、复制或覆盖下层规则与状态。

## 8. 历史快照与失效内容只读标注机制（`v1.1` 新增）

### 8.1 文档级历史快照判定标准与只读声明块
- **适用判定标准（三条中至少满足两条，且不再承担日常活状态更新）**：
  1. 所记录阶段、批次或工单已全面结案，或已被后续架构全面取代；
  2. 其原有活队列、任务明细或议题追踪职能已由现役单一权威源（如 `P8-PROJECT-TASKS v1.0`、`项目方案 v3.0 §8`、`P8-ALGO-REVIEW`）正式接管；
  3. 属于一次性立项报告、静态交接快照或已被合并并账的早期清单底稿。
- **操作硬禁令**：**零删除、零移动文件物理路径（保证全仓历史引用不断链）、零修改既有正文与数字**。
- **标准只读声明块（统一插入文档首行 `# 标题` 正下方）**：
  ```markdown
  > ⚠️ **历史快照（只读留档 · YYYY-MM-DD 标定）**：本文档反映 **[阶段/日期]** 之历史事实或一次性交付记录，依据《项目编号与命名规范 §8.1》冻结留档——**严禁回改正文、严禁删除或移动路径**。当前实时权威状态/对应现行规范请跳转：[`<现役权威文档名称>`](<相对路径>)。
  ```

### 8.2 节级失效 / 被取代内容只读标注块
- 当仅文档内某一节（而非整份文档）因后续裁决、协议升版或架构切换而被取代时，在**被取代节标题正下方**插入如下 blockquote 标注块：
  ```markdown
  > ⚠️ **本节内容已失效/被取代（YYYY-MM-DD 标定）**：[事由一行]。现行权威：<文档名+节号+锚点>。原文按冻结规则保留，本标注为唯一合法编辑。
  ```
- **硬约束**：仅插入标注块，原文字句零改动；插入本标注块不计入“修改历史正文”违例。

### 8.3 被取代内容同提交加注纪律
- 凡新裁决、协议改版或架构变更使另一在档文档之节内容被取代，**必须在同一 Git 提交内**为被取代节插入 `§8.2` 标注块（或整份满足 `§8.1` 者插入 `§8.1` 声明块）。
- 对应交付回签必须单列 **“被取代内容同提交加注清单（文件 + 节）”**；缺列视为回签不完整（注：本机制落盘前的存量历史失效内容通过专门追溯清点批补注，不追溯阻塞既有已闭合提交）。

## 9. 新建独立文档准入规则与审批路径（`v1.1` 新增）

1. **文件增殖判据前置核验（依 `AGENTS.md`）**：新建任何独立 `.md` 文档前，须书面核验满足 **“无既有文档可合理承载该职责”** 或 **“强行塞入既有文档将导致职责混杂”** 之一，否则一律在既有归属文档加节。
2. **命名与首部规范**：路径与文件名须符合 `§6` 模板；文档首部须载明治理编号/任务单号、法定文档锚点及在四层单一事实源中的职责边界。
3. **审批与指针挂载路径**：新建文档提案须随派工单呈管控席与用户批准；获批创建后，须同提交在对应索引位置（`项目方案 §8.2` / `P8-PROJECT-TASKS` / `STATUS.md` 视内容类型而定）建立可达链接；未经批准严禁擅自新建独立文档。

## 10. 文档整合 / 归并 / 归档操作规程（`v1.1` 新增）

1. **并账清点**：执行多份文档归并或职责迁出前，须逐条核查源文档中全部未关闭条目，显式登记去向（`迁入目标档编号 + 节号` 或 `已过时销项依据`），严禁静默遗漏。
2. **留痕替代删除**：源文档并账完成后，优先**原地保留并加注 `§8.1` / `§8.2` 声明块及去向指针**，不随意删除或重命名，防止全仓链接断裂。
3. **物理归档条件**：仅当确认文档已彻底脱离活跃索引且经用户明确批复移入 `docs/archive/` 时，方可执行 `git mv`，并须同步更新 `docs/archive/README.md` 及修复全仓断链引用。
4. **可机读同步**：任何修改触及 [`P8-PROJECT-TASKS_全量任务分解台账.md`](audit/P8-PROJECT-TASKS_全量任务分解台账.md) 时，须严格按 `AGENTS.md` 执行 `render_progress_board.py` 刷新与 `--check` 校验。
