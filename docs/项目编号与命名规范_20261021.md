# 项目编号与命名规范（治理基线）

> **正式确定日期（生效起点）**：2026-10-21，由用户在 V1 2019 双城盲测复核支线拍板确立。
> **性质**：编号/命名基线规则；与最高铁律《AGENTS.md》冲突时以《AGENTS.md》为准。
> **适用**：2026-10-21 之后新开立的 Issue、工单、核验单、任务书、文档标题。已封盘/已 push 的历史件按冻结规则不回改，仅在本规范 §4 做新旧号映射加注。

## 1. 两套体系，禁止混用

项目工作编号分两条互不相混的线。先判断动作属于哪一类，再选编号，不得自创第三套临时号。

### A 线 · 开发交付树（GitHub Issue，Phase 2 起强制）

面向**要写/改生产代码**的交付，自上而下三层：

| 层 | 名称 | Issue 标题格式（全拼前缀，禁止孤立简称） |
| :-- | :-- | :-- |
| 1 | Phase X | 阶段（Phase 1 数据/模型地基、Phase 2 交易工程……） |
| 2 | Task YY | 阶段内任务，对应一个 Spec 主 Issue：`Spec: Phase X Task YY - <描述>` |
| 3 | Ticket ZZ | 可独立演示的垂直切片：`Phase X Task YY - Ticket ZZ: <type>(<scope>): <描述>`，带 `Blocked by` 依赖 |

- 权威出处：《AGENTS.md》「Task 与 Ticket 显式全拼命名原则」、`docs/spec-update-process.md` §3.2。
- Phase 1 历史的小数点编号 `Task 1.1 / 1.2` 为冻结历史，向前兼容，不回改。

### B 线 · 治理 / 审计线（不进交付树）

面向**只读复核、核验、裁决、封盘、文档对账**等不动生产代码的动作，用治理工单 + 核验单/裁决单编号：

| 类别 | 格式 | 示例 |
| :-- | :-- | :-- |
| 治理工单 / 议题 | `Pn-NAME`（n 为治理批次，NAME 大写下划线短码） | `P7-W1-POOLPHASE`、`P6-TMIN-CV-LOCK` |
| 核验单 | `<父工单>-CHK-ZZ` | `P4-BLIND-AUDIT-CHK-01` |
| 裁决单 / 决议 | `<父工单>-VERDICT-RZ` 或沿用既有裁决令格式 | `P7-W1-B-CLOSURE-VERDICT-R1` |
| 波次（时序，非层级） | `W1 / W2 / W3`，见 `docs/ROADMAP.md` | 不得当作编号层级嵌套 |

- **B 线文档主编号只用 `Pn-NAME-CHK-ZZ`；A 线 `Ticket ZZ` 仅可出现在描述后缀与正文锚点中，不得作为主编号段。** 复核 A 线交付物的 B 线单据，正文首页必须写明对应 A 线 Issue 号。
- **纯审计复核不新开开发 Ticket**，不套 Phase-Task-Ticket。
- 实验内部步骤（对照、诊断子项）可作子名保留，但**不得单独充当工单/文档主编号**。

## 2. 硬性禁止项

1. 禁止自创 `T3`、`P-1/P-2/P-3`、`E8-a/E8-b`、`D-1/D-2`、`L0/L1/L2` 这类脱离两套体系的临时号作为工单或文档主标题。
2. 禁止 B 线审计项塞进 A 树（不为纯复核开 `Phase X Task YY - Ticket ZZ`）。
3. 禁止 A 线 Task/Ticket 使用孤立简称（单独 `Ticket 01`、隐式缩写）。
4. 禁止同一文件/工单跨线混用两种编号体系。
5. 已封盘历史件不回改文件名与正文，只在本规范或台账加映射注。

## 5. 后续执行

- 每新开一项，先判 A/B 线，再取号；审核方在任务书首页写明所属工单/核验单号。
- 父工单短码 `P4-BLIND-AUDIT` 已于 2026-10-21 用户确认定稿，CHK-01/02/03 序列见 §3。
- **审计纪律（2026-10-26 CHK-16 确立）**：
  1. 审计单据中的 `git diff` 命令，基线不得使用 `origin/main`（推送后退化为恒空）；必须写明具体 commit SHA 或 `HEAD~N`。
  2. 命令字符串落盘前必须实跑一次，并附输出；凡「输出为空即通过」的判定，须证明该命令在非退化基线下执行。
  3. 审计单据内一切数值必须标注采集方（复核方实测 / 开发端自测），不得混用。
  4. 正文与指令必须自洽：复核方起草时应保证正文条目与指令描述逐条对应，避免下游按指令补齐形成序号歧义。
